# Task 12 — Negative-path / diagnostic evidence

## Empty Pareto frontier root cause

### Observation
All 5 scenario DSEs (lpddr5_3b, lpddr5x_7b, hbm2e_7b, onchip_7b, onchip_7b_chat)
reported `frontier=0` despite 60–66 design points evaluating successfully with
`complete=60–66` and `failed=0`.

### Diagnosis
The root cause was the AUTHORITATIVE hard gate in `sim/dse/pareto.py`.
`MultiObjectivePareto.evaluate_gates()` required every result to have
`trust_level == authoritative` before it could enter the Pareto frontier.

In exploratory mode the scenario DSE runner produces `exploratory` trust-level
results because the calibration registry marks most current calibration IDs as
T0/T1. Consequently every complete result failed the AUTHORITATIVE gate and the
frontier was empty.

This is a pre-existing DSE Pareto-filter issue, not a bug introduced by Todos
1–11. It affected the legacy `lpddr5_3b` scenario as well as the new scenarios.

### Fix applied
1. `sim/dse/pareto.py`: relaxed the AUTHORITATIVE gate so that, by default, only
   `non_authoritative` (partial/error) results are excluded. In quality-gate mode
   the gate still requires authoritative results.
2. `sim/dse/runner.py`: populated `EngineMetrics.completed_throughput_hz` from
   `ScenarioMetrics.completed_throughput_hz` so the primary Pareto objective is
   no longer `-inf` for every point.
3. `sim/tests/test_scenario_pareto.py`: updated the non-authoritative test to
   assert that exploratory results are allowed by default and only
   non_authoritative results are excluded.

### Additional finding: scenario bandwidth was not bound to DSE axis
Before the fix, all 5 scenarios explored the same full `bandwidth_gbps` axis
([25.6, 51.2, 102.4, 204.8, 460.0, 819.2]), so their per-scenario rankings were
identical. This prevented the requested continuity verification.

To enable continuity analysis within Todo 12:
1. Added scenario-specific `memory`/`constraints` metadata in
   `sim/dse_scenario.py:_build_scenario_model()`.
2. Added a dynamic `scenario_bandwidth_match` constraint in
   `sim/dse/space.py:DesignSpace.__init__()` that pins the `bandwidth_gbps` axis
   to the scenario's declared bandwidth.
3. Extended `sim/config/dse_axes.yaml` `bandwidth_gbps` values to include the
   scenario-specific bandwidths (68.0, 410.0, 500.0) so the constraint can be
   satisfied exactly.

This is a constraint-parsing / scenario-binding fix, not a change to engine
physics or calibration constants.

### Verification after fix
- All 5 scenario DSEs exit 0.
- Frontier sizes: lpddr5_3b=3, lpddr5x_7b=3, hbm2e_7b=6, onchip_7b=6,
  onchip_7b_chat=6.
- Engine preference transition:
  - lpddr5_3b (51.2 GB/s): block wins
  - lpddr5x_7b (68 GB/s): os_systolic wins
  - hbm2e_7b (410 GB/s): os_systolic wins
  - onchip_7b (500 GB/s): os_systolic wins
  - onchip_7b_chat (500 GB/s): os_systolic wins

The transition from block at low bandwidth to os_systolic at medium/high
bandwidth demonstrates that sequential/random DRAM efficiency differences
produce observable ranking impact: wide engines that can exploit higher
bandwidth overtake area-efficient engines as external bandwidth rises.
